# Windows 采集线程的停止与资源所有权

## 已证实的问题

Windows 系统声音的 `stop()` 原来在 Tokio future 中直接销毁 CPAL stream。
本仓库 WASAPI 的析构函数同步等待音频线程退出，因此外层两秒 `timeout`
不能中断这次 poll。设备重绑定也会在异步 monitor 内走同一条释放路径。

离线固定 join 样本在单线程和双线程 Tokio 上均复现：25 ms 的 timeout
分别在 184.108/185.135 ms 后返回成功；后台释放的对照约 30 ms 返回超时，
但直到 join 真正完成才允许再次启动。这证明超时保护失效，不证明它导致
issue #329 的 30–40 秒字幕累积，也不是 Windows 驱动实机验收。

## 选择与不变量

仅增加 timeout 不能抢占同步 native 调用。仅把 drop 放进 `spawn_blocking`
还要分别处理停止、重绑定、播放失败和取消构建的所有权，并保留尚未完成的
释放状态；无法退出的 blocking job 也可能阻碍 runtime 退出。

采用与现有麦克风和 Windows 应用采集相同的专属线程模式：一个 owner
串行执行设备解析、构建、播放、每秒重绑定及销毁。异步入口只等待启动结果
或退出完成，所有 native 资源都在线程上释放。

- slot 在 owner 完成前保留，正常运行时拒绝重复启动，取消后返回
  `PreviousCaptureStopping`。超时仅结束等待，不宣称驱动已被强制终止。
- 启动 future 被取消、停止或最后一个外部 capture 被释放，都标记取消；
  owner 不持有 slot，避免它自行保活而无法触发最后一次取消。
- `finished` 在 native stream 析构完成后才发布。取消、播放失败、重绑定
  和设备故障共用这一保证，不能在释放旧设备前开启新 stream。
- 活动标记、设备名和音频统计属于单个 worker。旧 worker 完成时不能清空
  新会话状态；取消后的回调不再投递音频或报告过期故障。
- PCM 格式、重采样、队列、来源选择算法、权限和提供商逻辑保持原语义。

## 验证边界

使用真实阻塞析构的离线回归覆盖超时、启动中取消、重复停止、失败释放及
再次启动。Windows CI 验证原生适配层编译与测试；既有显式 native tone
用例改走生产 start 入口。没有 Windows 实机时，驱动卡住、设备切换和真实
字幕链路继续列为待验收；额外 API 回放无法验证这些 Windows 边界。
