# Audio3 补静音时间轴修复

关联 #329。用户反馈 Windows 阿里云长会话字幕延迟逐渐增加；具体模式与
真实服务根因仍待确认。本修复针对独立可复现的音频时长重复累积边界。

## 失败场景与目标

原生回调可能延迟后批量补交 PCM。发送队列为空，不代表那段时间没有被
捕获：旧 Audio3 心跳只看最近一次发送时刻，每 100 ms 空窗可能补入静音，
之后仍发送覆盖相同时段的完整真实 PCM。重复的回调空窗可不断增加发送
到服务的音频时长。

目标是限制合成静音造成的累计超前，保留真实 PCM 的完整内容和顺序。
不改翻译模型、断句、字幕历史、重连阈值或系统捕获行为。

## 方案

在共享 `audio3_client.rs` 中维护每次服务任务的单调起点和已发送音频的
虚拟结束位置，包含真实 PCM 和合成静音。任务开始前的连接等待不计入
音频时间轴。只有发送音频进度比单调时间落后至少一个静音块，且满足现有
idle、pending PCM、结束状态与错误检查时，才补入静音。

每个成功包按精确 PCM 帧时长推进音频结束位置，最低推进至该包开始发送
的时刻，丢弃此前没有发送的历史静音欠账。否则长时间空闲中漏掉的心跳
会变成恢复讲话后可继续消费的静音额度，仍导致音频被拉长。

时长使用整数纳秒，避免小包逐次换算毫秒的截断误差。额度检查、发送和
成功计账服从同一个 writer 串行顺序；失败或取消不能提前记为成功。真实
PCM 不受额度限制，不丢弃、不截断、不重排。清空字幕保留该任务时间轴，
重新连接建立新的任务起点。

相比单纯增大 idle 阈值，这个方案不依赖原生回调必须准时；相比丢弃迟到
PCM，它不会删去真实语音。它不能撤回已经发送的静音，也不声称消除网络、
服务处理或显示阶段的所有延迟。

## 验证与交付

1. 本地 WebSocket 运行旧实现：固定每 200 ms 提交 200 ms 非零 PCM，累计
   服务收到的真实/静音字节，证明额外静音随批次数增长。旧码已测得约
   2,002 ms 墙钟内发送 64,000 字节真实音频和 35,200 字节额外静音，
   即 2 秒真实输入被发送成 3.1 秒音频。
2. 相同场景复测修复；增加长时间模拟、细小包精度、真实静音、setup、清空、
   重连、待发 PCM、发送失败与收尾边界回归。
3. 运行共享 Rust 格式、Clippy、测试及架构检查，实际 Android host JNI/JVM
   检查；CI 验证 Windows/macOS/Linux 与 Android 的共同实现。
4. 独立审查后提交 PR。记录可复现的修复及真实 Windows/服务验收边界，不
   自动关闭 #329 或将其标为已在反馈者环境解决。
